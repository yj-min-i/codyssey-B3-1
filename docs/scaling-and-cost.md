# 확장·비용 대응 계획

현재 구조는 **EC2 `t3.micro` 1대 + 서버 디스크의 SQLite**입니다. 이 문서는 트래픽이 늘었을 때 병목을 어떻게 찾고, 언제·어떻게 ALB를 도입하며, 비용을 어떻게 감시할지 정리합니다.
이번 미션에서는 프리 티어 범위를 지키기 위해 **구현하지 않고 계획으로만** 둡니다(ALB·NAT·RDS는 켜 두는 것만으로 과금).

---

## 1. 현재 구조의 한계

| 구성 요소 | 한계 | 영향 |
|---|---|---|
| EC2 `t3.micro` 1대 | vCPU 2개(버스터블)·메모리 1GiB. CPU 크레딧이 바닥나면 기준 성능으로 떨어짐 | 동시 접속이 늘면 응답 지연, 메모리 부족 시 앱 종료 |
| 서버 1대 · AZ 1개(`2a`) | 단일 장애점 | 서버나 AZ에 문제가 생기면 서비스 전체 중단 |
| SQLite (`/opt/fatelia/data/fatelia.db`) | DB가 서버 디스크 파일에 묶임 | 서버를 2대로 늘리면 데이터가 나뉘어 **수평 확장 불가** |
| 자동 할당 퍼블릭 IP | 중지·시작 시 바뀔 수 있음 | 주소 변경 시 접속 불가 |

## 2. 병목 진단: 지표와 확인 방법

| 지표 | 어디서 보나 | 경고 기준(예시) | 해석 |
|---|---|---|---|
| CPU 사용률 `CPUUtilization` | CloudWatch(EC2 기본 지표) | 15분 이상 70% 초과 | 연산 부족 → 수직 확장 검토 |
| CPU 크레딧 잔량 `CPUCreditBalance` | CloudWatch(T 계열 인스턴스) | 0에 가까워짐 | 버스트가 끝나 성능 저하 직전 |
| 메모리·스왑 | 서버에서 `free -h` (CloudWatch 기본 지표에는 없음, Agent 설치 필요) | 스왑 사용이 계속 늘어남 | 메모리 부족 |
| 응답 시간 | `curl -w "%{time_total}\n"`, nginx 액세스 로그 | 평소보다 크게 늘어남 | 서버 또는 앱 지연 |
| 5xx 오류 | nginx 액세스 로그 | `502` 반복 | 앱(Node)이 죽었거나 과부하 |
| 디스크 | `df -h` | 80% 이상 | 로그·DB 증가 |

> 현재 IAM 정책(`B3-1-LeastPrivilege`)에는 CloudWatch 권한이 없어 콘솔 모니터링 탭이 보이지 않습니다. 지표를 보려면 `cloudwatch:GetMetricData`, `cloudwatch:ListMetrics` **읽기 권한만** 추가합니다.

**진단 순서** (바깥 → 안쪽)

```bash
# 1) 외부에서 응답 시간 측정 (Mac)
curl -o /dev/null -s -w "HTTP %{http_code}  %{time_total}s\n" http://<퍼블릭IP>/

# 2) 서버 자원 (EC2)
uptime                # load average
free -h               # 메모리·스왑
df -h /               # 디스크

# 3) 웹 서버 오류 (EC2)
sudo tail -n 200 /var/log/nginx/access.log | awk '{print $9}' | sort | uniq -c   # 상태 코드 분포
sudo tail -n 50 /var/log/nginx/error.log

# 4) 앱 로그 (EC2)
sudo journalctl -u fatelia -n 50 --no-pager
```

판단: **자원 부족**(CPU·메모리)이면 먼저 수직 확장, **가용성·동시 처리 한계**면 ALB + 다중 인스턴스로 넘어갑니다.

## 3. ALB 도입 기준

아래 중 하나라도 해당하면 도입을 검토합니다.

- 인스턴스를 한 단계 키워도(`t3.small` 등) CPU·메모리 경고가 계속될 때
- 서버 1대 장애로 서비스가 멈추면 안 되는 요구(가용성)가 생길 때
- 배포 중에도 서비스를 멈추지 않아야 할 때(무중단 배포)
- HTTPS 인증서를 관리형(ACM)으로 처리하고 싶을 때

**선행 조건**: 서버를 여러 대로 늘리려면 상태를 서버 밖으로 빼야 합니다.
SQLite → RDS 같은 외부 DB, 로그인 세션 → 쿠키 또는 외부 저장소, 업로드 파일 → S3.

## 4. ALB 설계안

```
인터넷 → ALB (퍼블릭 서브넷 2a·2c, SG: 80/443 ← 0.0.0.0/0)
        → 대상 그룹 (헬스체크 GET /health)
        → EC2 Auto Scaling 그룹 (최소 2대, 2a·2c 분산, SG: 80 ← ALB의 SG만)
        → RDS (DB 서브넷, SG: DB 포트 ← EC2의 SG만)
```

- ALB는 **가용 영역 2개 이상의 서브넷**이 필요하므로 퍼블릭 서브넷을 `2c`에 하나 더 만듭니다.
- EC2 보안 그룹의 80번 소스를 `0.0.0.0/0`에서 **ALB 보안 그룹**으로 바꿔, 서버에 직접 접속하는 길을 막습니다.
- 헬스체크는 지금처럼 nginx가 `OK`만 돌려주면 앱이 죽어도 정상으로 보이므로, **앱과 DB 연결까지 확인하는 `/health`**로 바꿉니다.
- 더 안전하게 하려면 EC2를 프라이빗 서브넷으로 옮기고 NAT Gateway로 아웃바운드를 처리합니다(NAT는 추가 과금).

## 5. 비용 감시

**확장 시 새로 생기는 비용 항목**

| 항목 | 과금 방식 |
|---|---|
| ALB | 실행 시간 + 처리량 단위(LCU) |
| 추가 EC2·EBS | 인스턴스 시간 + 볼륨 용량 |
| NAT Gateway | 실행 시간 + 처리한 데이터 양 |
| RDS | 인스턴스 시간 + 스토리지 |
| 퍼블릭 IPv4 | 주소당 시간 단위 |
| 데이터 전송 | 인터넷으로 나가는 트래픽 |

**감시 방법**

- **AWS Budgets**: 월 예산을 정하고 실제·예상 비용이 기준(예: 80%)을 넘으면 이메일 알림.
- **Cost Explorer**: 서비스별·일별 비용 추이 확인.
- **비용 할당 태그**: 모든 리소스에 붙인 `Project=b3-1` 태그를 결제 콘솔에서 활성화하면 이 프로젝트 비용만 따로 볼 수 있음.
- **Free 플랜 크레딧 위젯**: 남은 크레딧과 플랜 만료일 확인.

> 결제 화면은 루트 또는 결제 권한이 있는 사용자만 볼 수 있습니다. 이번 실습은 루트 사용을 최소화하는 원칙에 따라 확인하지 않았고, 실제 운영이라면 결제 조회 전용 권한을 가진 별도 사용자를 둡니다.

## 6. 단계별 확장 로드맵

| 단계 | 언제 | 조치 | 추가 비용 |
|---|---|---|---|
| 0 (현재) | 실습·포트폴리오 | `t3.micro` 1대 + nginx + SQLite | Free 플랜 크레딧 내 |
| 1 | CPU·메모리 경고 | 인스턴스 크기 상향(수직 확장) | 인스턴스 요금 증가 |
| 2 | 서버를 2대 이상으로 늘려야 할 때 | DB를 RDS로, 세션·파일을 서버 밖으로 분리 | RDS·S3 |
| 3 | 가용성·무중단 배포 요구 | ALB + Auto Scaling(2개 AZ), HTTPS(ACM) | ALB·EC2 추가 |
| 4 | 정적 파일 트래픽 증가 | 이미지·JS를 S3 + CloudFront로 | 전송량 기준 |
